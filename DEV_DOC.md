## 1. Architecture overview

```
                         host : 443 (TLS)         host : 2121 (+30000-30010 PASV)
                              │                         │
                        ┌─────┴─────┐               ┌───┴───┐
   internet  ─────────► │   nginx   │               │  ftp  │
                        └─────┬─────┘               └───┬───┘
        ┌────────────┬────────┴────────┐                |
        /         /resume/         /grafana/            │
   ┌────┴────┐  ┌────┴────┐       ┌─────────┐           │
   │wordpress│  │ resume  │       │ grafana │           │
   │ php-fpm │  └─────────┘       └────┬────┘           │
   └──┬───┬──┘                         │ queries        │
      │   │                       ┌────┴──────┐         │
 ┌────┴┐ ┌┴──────┐                │prometheus │         │
 │redis│ │mariadb│                └────┬──────┘         │
 └─────┘ └───────┘                     │ scrapes        │
                                  ┌────┴─────┐          │
                                  │ cadvisor │          │
                                  └──────────┘          │
   wordpress_data ◄─────────────────────────────────────┘   (shared volume)
   mariadb_data   ◄── mariadb

   All containers on the user-defined bridge network: inception_network
```

- **nginx** is the only public entry point (443, TLS 1.2/1.3). It proxies `/` to
  WordPress (php-fpm on `:9000`), `/resume/` to the resume app, `/grafana/` to
  Grafana, and serves the WordPress files from the shared volume.
- **ftp** mounts the same `wordpress_data` volume as nginx/wordpress.
- Monitoring chain: **cadvisor → prometheus → grafana**.

## 3. Set up the environment from scratch

### Prerequisites
- Linux host/VM with **Docker** + **Docker Compose** plugin.
- `make`, `openssl`, `curl`. `mkcert` is optional (the setup script downloads it
  if absent).
- Local DNS for the domain:
  ```bash
  echo "127.0.0.1 aazzaoui.42.fr" | sudo tee -a /etc/hosts
  ```

### Configuration files
- **`srcs/.env`** — non-secret settings, e.g.:
  ```
  NGINX_PORT=443        PHP_FPM_PORT=9000     MARIADB_PORT=3306
  DB_NAME=wordpress     WP_DB_USER=wp_user    DB_HOST=mariadb:3306
  WP_ADMIN=wp_owner     USER=aazzaoui         USER_HOST=aazzaoui.42.fr
  REDIS_PORT=1024       FTP_PORT=2121         pasv_min_port=30000  pasv_max_port=30010
  CADVISOR_PORT=8080    PROMETHEUS_PORT=9090  GRAFANA_PORT=3000
  GF_SECURITY_ADMIN_USER=aazzaoui
  ```
  > The admin username `wp_owner` deliberately avoids `admin`/`administrator`
  > (subject rule).

- **`srcs/secrets/`** — generated by `tools/setup.sh`, never committed. Contains
  the TLS pair, all passwords, and WordPress salts. Mounted into containers as
  Docker secrets at `/run/secrets/<name>`.

### What `tools/setup.sh` does (run automatically by `make`)
1. Creates `srcs/secrets/` (idempotent — only runs if it doesn't exist).
2. Gets/downloads `mkcert`, installs a local CA, issues `nginx.crt` / `nginx.key`
   for `aazzaoui.42.fr` + `127.0.0.1`.
3. Generates all passwords with `openssl rand -base64`.
4. Fetches WordPress salts from the official API into `salts.txt`.
5. Creates `~/data/mariadb`, `~/data/wordpress`, and `~/data/prometheus` (volume backing dirs).

To regenerate everything: `make fclean && make`.

> Note: the `Makefile` hardcodes `HOME = /home/aazzaoui`. On another machine,
> update that line (and the `.env` `USER`/`USER_HOST` + the `/etc/hosts` entry).

## 4. Build and launch (Makefile + Compose)

`make` = `setup` + `docker compose ... up -d --build`.

| Target | Effect |
|--------|--------|
| `make` / `make run` | run `setup.sh`, then build & start all services (detached) |
| `make start` | `docker compose start` (existing containers) |
| `make stop` | `docker compose stop` |
| `make clean` | `down --rmi all --remove-orphans` |
| `make fclean` | `down --rmi all --volumes --remove-orphans` + delete `srcs/secrets` and `~/data` |
| `make re` / `make fre` | clean/fclean, then run |

Direct Compose (all need `-f srcs/docker-compose.yml`):
```bash
docker compose -f srcs/docker-compose.yml up -d --build          # build + start
docker compose -f srcs/docker-compose.yml up -d --build nginx    # one service
docker compose -f srcs/docker-compose.yml build --no-cache wordpress
docker compose -f srcs/docker-compose.yml config                 # validate/expand
```

## 5. Managing containers and volumes

```bash
CF="-f srcs/docker-compose.yml"

# Status & logs
docker compose $CF ps
docker compose $CF logs -f [service]

# Lifecycle
docker compose $CF restart [service]
docker compose $CF stop [service]
docker compose $CF down                 # stop & remove containers (keep volumes)

# Shell into a container
docker exec -it wordpress sh
docker exec -it mariadb sh

# Volumes & network
docker volume ls                        # srcs_mariadb_data, srcs_wordpress_data, srcs_prometheus_data
docker volume inspect srcs_wordpress_data
docker network inspect inception_network
```

WordPress via WP-CLI:
```bash
docker exec wordpress wp plugin list --allow-root --path=/var/www/html
docker exec wordpress wp user list --allow-root --path=/var/www/html
docker exec wordpress wp redis status --allow-root --path=/var/www/html
```

Database:
```bash
docker exec -it mariadb mariadb -uroot -p"$(cat srcs/secrets/db_root_password.txt)"
docker exec mariadb mariadb-admin ping -uroot -p"$(cat srcs/secrets/db_root_password.txt)"
```

## 6. Where data is stored and how it persists

Three **named volumes**, declared in the top-level `volumes:` block of
`docker-compose.yml`, backed by `~/data` via the `local` driver's `o: bind`
option (the only way to pin a named volume to a chosen host path — it stays a
named volume, not a service-level bind mount):

| Volume | Mounted in | Host backing path | Contents |
|--------|-----------|-------------------|----------|
| `mariadb_data` | mariadb `/var/lib/mysql` | `~/data/mariadb` | the database |
| `wordpress_data` | wordpress, nginx, ftp `/var/www/` | `~/data/wordpress` | WordPress core + uploads + `wp-config.php` |
| `prometheus_data` | prometheus `/var/lib/prometheus` | `~/data/prometheus` | the TSDB (metrics history) |

Persistence behaviour:
- `make stop` / `make clean` / `down` → **data survives** (volumes and `~/data`
  are kept).
- `make fclean` (`down --volumes` + `rm -rf ~/data` + `rm -rf srcs/secrets`) →
  **data is destroyed**; the next `make` reinstalls WordPress and regenerates
  credentials from scratch.

Ephemeral by design (no volume): **redis** (cache rebuilds from MariaDB),
**grafana** (datasource and dashboard are re-provisioned on each boot).

## 7. Service start order & readiness

- `depends_on` in compose orders **startup** only (not readiness): wordpress →
  mariadb + redis; nginx → wordpress + resume + grafana; prometheus → cadvisor.
- True readiness is handled in code: `wordpress/tools/script.sh` polls MariaDB
  (`SELECT 1`, up to 60×1s) before running `wp core install`.
- Every entrypoint ends with `exec <daemon>` so the daemon is **PID 1** and
  receives signals directly; `init: true` (tini) reaps zombies. No infinite-loop
  keep-alive hacks.

## 8. Conventions & gotchas

- **Base image:** `alpine:3.23` for all services except **cadvisor**
  (`debian:bookworm-slim`, because the cAdvisor binary is glibc-linked).
- **Image tags:** `<service>:Inception` — never `latest`.
- **Secrets:** read from `/run/secrets/<name>` inside containers; never in
  Dockerfiles, env, or git. Don't `echo` them into logs.
- **First-boot guards:** entrypoints check for an existing config/marker (e.g.
  `/etc/my.cnf`, `/var/www/html/index.php`) so re-runs don't reinstall — to force
  a clean rebuild, `make fclean`.
- **Adminer** is wired into `docker-compose.yml` (depends on `mariadb`) and
  reachable through NGINX at `/adminer/`.
- **Portability:** the hardcoded `HOME` in the `Makefile` and the `aazzaoui`
  login throughout `.env` must be changed for a different user/host.

## 9. Troubleshooting

- **WordPress install fails / DB errors** — check `logs mariadb` is `Up` and the
  `db_password` secret matches; the readiness loop will abort after 60s.
- **502 from NGINX on `/`** — php-fpm not up yet or wrong `PHP_FPM_PORT`; check
  `logs wordpress`.
- **`/grafana/` broken assets** — `serve_from_sub_path`/`root_url` must match the
  NGINX `location /grafana/` proxy.
- **Prometheus target DOWN** — confirm cadvisor is `Up`, same network, port 8080.
- **Volume changes not taking effect** — first-boot guard or stale volume; reset
  with `make fclean`.
- **Permission denied on secrets** — confirm the file exists in `srcs/secrets/`
  and is listed under both top-level `secrets:` and the service.
